# Частина 1. Аналітичний звіт

## 1.1 Що це таке і які задачі вирішує

P-3 (Fenix) — це **drop-in стартер-кіт для Claude Code**, який накладається поверх будь-якого
багатомодульного проєкту. Він не містить runtime-коду: це набір markdown-інструкцій (slash-команди,
визначення субагентів, шаблони документів) плюс bash-інсталятор. Уся «логіка» виконується самим
Claude, який читає ці файли як промпти.

Кіт закриває чотири задачі:

1. **Децентралізована документація** за метафорою wings/rooms/drawers — доки живуть поряд з кодом
   (`<module>/docs/`), мають фронтметадані зі списком джерельних файлів і датою/комітом останнього
   рев'ю. Індексація, перевірка свіжості та заповнення заглушок автоматизовані через субагентів.
2. **Маршрутизація задач** (`task-router.md`) — класифікує запит за категоріями і підвантажує в контекст
   тільки релевантні rooms/references замість усієї документації. Це боротьба з роздуванням контексту.
3. **Файловий dev-workflow** architect → worker → tester. Кожна фаза пише артефакт на диск у
   `tasks/<task_id>/` (план, лог виконання, рев'ю, підсумок). Чат отримує лише короткі вказівники.
4. **Manifest-driven встановлення/видалення** — кожна дія інсталятора пишеться в `.fenix-manifest.json`,
   що дозволяє `/fx-uninstall` зробити чисте зворотне видалення з відновленням попередніх файлів.

Поверхня API: 6 slash-команд (`/fx-init`, `/fx-info`, `/fx-doc`, `/fx-task`, `/fx-agent`, `/fx-uninstall`)
і 7 субагентів. Орієнтований явно на KMP/Gradle-стек (auditor читає `build.gradle.kts`, розрізняє
Koin/Hilt, SQLDelight/Room).

## 1.2 Як він влаштований

### Компоненти в репозиторії

| Каталог | Вміст | Призначення |
|---|---|---|
| `scripts/setup.sh` | 588 рядків bash | Інсталятор: копіює кіт у `.claude/`, `docs/`, `docs-meta/`, пише маніфест, робить бекап існуючих `CLAUDE.md`/`.claude/`, детектить і застосовує апгрейд |
| `scripts/install-online.sh` | one-liner-інсталятор | Резолвить останній реліз з GitHub API, качає zip, делегує в `setup.sh` |
| `scripts/upgrades/*.json` | конфіг переходів | Попарні апгрейди `<from>-to-<to>` зі списками `replace`/`preserve`/`create_if_missing`/`remove` |
| `claude-commands/*.md` | 6 файлів | Визначення slash-команд (інструкції для Claude) |
| `claude-agents/*.md` | 7 агентів + `<name>-rules.md` + `_topology.md` | Субагенти з редагованими файлами поведінки |
| `templates/*.md` | 14 шаблонів | Форми для CLAUDE.md, rooms, drawers, task-артефактів тощо |
| `build/make-zip.sh` | пакувальник | Збирає `dist/p3-fenix-<ver>.zip`, версія тягнеться з `setup.sh` як єдине джерело |

### Потік роботи

```
setup.sh  →  /fx-init (скафолдинг зі заглушками)  →  /fx-doc audit (auditor читає код,
пропонує контент)  →  /fx-doc update (заповнення + лінкування)  →  /fx-task new (dev-цикл)
```

Ключове архітектурне рішення — **файловий «message bus»**. Субагенти в Claude Code працюють у
свіжому ізольованому контексті й не можуть напряму спілкуватися, тому весь обмін станом іде через
файли в `tasks/<id>/`. Це грамотний обхід обмежень платформи, а не випадковість.

### Розподіл прав

Тільки `worker` має право писати код проєкту; `architect` і `tester` — read-only на коді й пишуть
лише свій артефакт. Doc-агенти ніколи не редагують реальні доки — лише пропонують у `_pending/`.
Кожна фаза має human-approval gate. Це консервативна й безпечна модель.

## 1.3 Сильні сторони

- **Принцип «пропонуй, але не застосовуй»** наскрізний: жодних авто-правок документації чи коду без
  явного підтвердження людини. Для AI-кіта це правильний дефолт.
- **Чесна обробка фактів архітектором**: розділення на «Verified facts» і «Assumptions» — пряма реакція
  на реальний інцидент з неправильною версією Koin. Рідкісний рівень епістемічної дисципліни.
- **Manifest-driven uninstall з бекапами** — реверс-обхід дій, відновлення `_claude_backup/`, preflight
  з попередженням про користувацький контент і готовими `git stash`-командами.
- **Контроль контексту** як наскрізна тема: маршрутизація, ліміт 70 рядків на док, AI-оптимізований
  формат, нагадування про `/clear`.
- **Захист `_claude_backup/`** трьома шарами (інструкція + `IGNORE_THIS_FOLDER.md` + `.claudeignore`).
- **Ідемпотентність інсталятора** і захист від даунгрейду (`version_lt` через `sort -V`).

## 1.4 Проблеми

### Реальні (підтверджені читанням коду)

**[Середня] Тиха втрата записів у маніфесті.** `manifest_append` будує Python-скрипт прямою
підстановкою змінних у рядок коду, а виклик завершується `2>/dev/null || true`. Шлях/ім'я проєкту зі
спецсимволом ламає літерал → запис у маніфест **тихо** провалюється → `/fx-uninstall` пропускає файли.
Помилка непомітна при інсталяції й вистрілює лише при видаленні. Фікс: передавати значення через
`env`/`argv`, не глушити помилки.

**[Середня] README не відповідає вмісту репозиторію.** Блок «Contents» досі описує стару структуру:
каталог `p3-fenix-3.0.0/`, команди названі `fenix-*.md` (реально `fx-*.md`), згаданий неіснуючий
`plan.md`, не згадано наявний `fx-uninstall.md`.

**[Низька] Залишкові 3.0.0 у «READ BEFORE FIRST».** Секція «What to do next» радить
`unzip p3-fenix-3.0.0.zip`.

**[Низька] Неповне прибирання порожніх каталогів** — `copy_if_missing` неявно створює батьківські теки,
але не реєструє їх; після uninstall можуть лишатися порожні `docs/` тощо.

**[Низька] Крихкість `sed` для імені проєкту** — `s/{{PROJECT_NAME}}/$PROJECT_NAME/g` зламається на
`/`, `&` у назві теки.

### Потенційні / архітектурні ризики

- **Іменування релізних тегів.** `install-online.sh` зрізає префікс `v`, але URL завантаження очікує тег
  без `v`. Якщо релізи затегати `v3.1.0` → 404. Неявний контракт.
- **Немає транзитивних апгрейдів.** Апгрейди попарні; стрибок 3.0.0 → 3.3.0 впаде, бо нема
  `3.0.0-to-3.3.0.json`.
- **Колізія імен rooms у маршрутизаторі.** Категорії = унікальні імена rooms по всіх wings; два модулі з
  `persistence.md` дають перетин.
- **М'які обмеження** (70 рядків, формат, заборона inline-discovery) тримаються лише на слухняності
  моделі, без механічного енфорсменту.
- **Freshness залежить від повноти `documents:`** — забуте джерело тихо не детектиться як застарілість.
- **Тон дефолтного `DISCLAIMER.md`** — неформальні повідомлення виводяться щосесії; для командного кіта
  варто зробити дефолт нейтральним.

# Частина 2. Діагностика продуктивності `/fx-doc audit` / `update`

Основна претензія команди за три тижні: аудит і апдейт **дуже повільні й палять багато токенів**, що
нівелює сам сенс документації (мати метадані, щоб не перечитувати код). Діагноз підтверджено читанням
`fx-doc.md` і `module-auditor.md`. Проблема не в реалізації агентів, а в тому, що **флоу аудиту не
використовує метадані як gate, що відсікає роботу**.

### Корінь проблеми — три рішення

**1. На кожен запуск спавниться аудитор на КОЖЕН модуль.** `fx-doc.md`, крок 5, дослівно: аудитор
дispatchиться «for each module — whether touched by the diff **OR existing in settings.gradle.kts**».
Незмінені модулі теж отримують повноцінного субагента. Вартість у токенах масштабується від кількості
модулів, а не від обсягу змін. Паралелізм рятує wall-clock частково, але токени — ні: N агентів = N×
витрат, плюс кожен читає свій `-rules.md`, `_topology.md` і весь wing на старті.

**2. Дешева перевірка свіжості відбувається занадто пізно.** Контракт `last_reviewed_commit` +
`documents:` дозволяє зробити `git log <commit>..HEAD -- <sources>` і миттєво сказати «нічого не
змінилось». Але ця перевірка (`module-auditor`, крок 4) виконується **всередині вже заспавненого
агента, після читання всього wing** (крок 1). Дешевий git-діфф у `fx-doc` крок 4 рахується — і потім
**ігнорується** для скоупінгу.

**3. Аудитор безумовно перечитує код.** Крок 5 («Drawers needed») — відкритий обхід `src/` на **кожному**
запуску без прив'язки до дельти. Після трьох тижнів більшість заглушок заповнено, але аудитор усе одно
спавниться на кожен wing, щоб вкотре підтвердити «це вже не заглушка».

Окремо: фаза `update` серійна і для stale-доків робить «Re-read wing fresh» — **повторно читає** те, що
аудит уже прочитав.

**Підсумок:** метадані є, але ніде не працюють як gate. Вони використовуються лише для класифікації
*всередині* дорогого шляху, а не для того, щоб у цей шлях не заходити.

# Частина 3. План оптимізації

За спаданням віддачі. Пункти A+B дають основний виграш і не змінюють зовнішню поведінку для користувача.

### A. Гейтити спавн аудиторів дельтою на рівні оркестратора *(найбільша віддача)*

Змінити `fx-doc.md` крок 5 з «усі модулі» на: взяти `git diff --name-only BASE..HEAD` і спавнити
аудитора **тільки** для модулів, чиї файли зі `documents:` потрапили в набір, плюс модулі з відомими
незаповненими заглушками. Після стабілізації кодбази це перетворює «N аудиторів завжди» на «0–2 на PR».

### B. Легкий кеш-стан, щоб не читати wings заради перевірки

Завести `docs-meta/.fenix-cache.json`: на кожен док — `last_reviewed_commit`, `documents:`, прапорець
`is_stub`. Оркестратор робить один дешевий прохід (git log по списку джерел) без читання прози чи коду й
вирішує, кого чіпати. Заповнені заглушки більше не ресканяться.

Орієнтовна схема кеша:

```json
{
  "generated_at": "<timestamp>",
  "head_commit": "<sha>",
  "docs": {
    "modules/feature/practice/docs/rooms/persistence.md": {
      "documents": ["modules/feature/practice/src/.../Db.kt"],
      "last_reviewed_commit": "ab12cd3",
      "is_stub": false
    }
  }
}
```

### C. Розчепити stub-fill і staleness

Це різні за вартістю операції. Заповнення заглушок — одноразова дорога річ. Свіжість — дешева
рекурентна перевірка. Зараз вони злиті, тож кожна перевірка свіжості тягне детекцію заглушок і скан
драверів. Після первинного заповнення детекцію заглушок вимикати за станом з кеша (`is_stub: false`).

### D. Дешеву команду зробити дефолтною, дорогу — явною

`/fx-doc freshness` (read-only, на git log, **не читає код**) має бути рутинною командою «що застаріло».
Дороге читання коду викликати точково: `/fx-doc update --only <module>` тільки для свідомо обраного
доку. Зараз `update` переаудитує все, перш ніж оновити будь-що.

### E. Подавати аудитору діфф, а не «йди прочитай весь src/»

Коли док справді stale, аудитору потрібен не весь модуль, а `git diff <last_reviewed_commit>..HEAD --
<documents:>` — конкретні зміни. Буквальне втілення тези: метадані (діапазон комітів) → читання дельти
замість перечитування коду.

### F. Винести drawer-walk (крок 5 аудитора) під окремий прапорець

`--suggest-drawers`, а не ганяти на кожному аудиті.

# Частина 4. Оцінка ефективності (токени / час)

> Це **модель**, а не бенчмарк: точні цифри залежать від кількості модулів, обсягу wing-доків і `src/` у
> приватному репо. Але головний важіль майже не залежить від цих невідомих.

### Фіксований оверхед на кожного аудитора (виміряно з кіта)

| Що читає аудитор на старті | ~токенів |
|---|---|
| `module-auditor.md` (визначення) | ~2 100 |
| `module-auditor-rules.md` | ~1 390 |
| `_topology.md` | ~1 000 |
| **Разом «boot»** | **~4 500** |

Плюс на кожного аудитора: читання всього wing (~3 000–4 000), безумовний drawer-walk по `src/`
(~3 000–8 000), системний промпт субагента, генерація proposal (output-токени дорожчі й повільніші).
Навіть **незмінений** модуль коштує ~12 000–15 000 токенів за прохід — і це множиться на кількість модулів.

### Модель

Ключ: **витрати ≈ (кількість заспавнених аудиторів) × (вартість одного)**. Поточний дизайн спавнить на
всі N модулів; фікс A+B — лише на k змінених. Коефіцієнт прискорення ≈ **N / k**.

Сценарій: N = 15 модулів, типовий PR зачіпає k = 2.

**Зараз (спавн на всі 15):**
- 13 незмінених × ~13k = ~169k
- 2 змінених × ~30k = ~60k
- **≈ 230k токенів на один `/fx-doc audit`**

**Після A+B (гейт по дельті + кеш):**
- дешевий прохід оркестратора (git diff + читання кеша) ≈ ~1–2k
- 2 змінених аудитори з фіксом E (діфф, а не весь `src/`) ≈ 2 × ~20k = ~40k
- **≈ 42k токенів**

➡ **~5–6× менше токенів (≈80% економії)** у типовому PR-сценарії.

Найчастіший випадок — **нічого не змінилось з минулого аудиту**: зараз усе одно 15 аудиторів (~195k,
кілька хвилин), після фіксу — нуль аудиторів, лише гейт (~1–2k, секунди). Тут економія **~99%**.

### Час

Латентність ≈ (кількість агентів, що мають відпрацювати) + (сумарні output-токени). Субагенти йдуть
паралельно, але конкурентність обмежена, а синтез і фаза `update` серійні. Перехід 15 → 2 агенти ≈
**3–6× по швидкості** у типовому PR; випадок «нічого не змінилось» — з хвилин у секунди. Найбільший
виграш не в середньому, а в прибиранні дорогих «порожніх» прогонів.

### Як перевірити на реальних числах

Claude Code показує витрати токенів за сесію. Зробити один `/fx-doc audit`, поділити фактичну цифру на
N → реальна вартість одного аудитора. Прискорення = N / k, де k — скільки модулів реально чіпає середній
PR (порахувати по `git diff --name-only` за останні 5–10 мерджів). Якщо модулів > 15 або PR-и точкові
(k = 1), виграш ще більший.

# Частина 5. Roadmap

| # | Зміна | Файли | Пріоритет | Виграш |
|---|---|---|---|---|
| A | Гейт спавну аудиторів по `git diff` | `fx-doc.md` (крок 5) | P0 | ~80% токенів |
| B | Кеш-стан `.fenix-cache.json` | новий файл + `fx-doc.md`, `module-auditor.md` | P0 | усуває читання wings заради перевірки |
| C | Розчепити stub-fill / staleness | `module-auditor.md`, `fx-doc.md` | P1 | прибирає re-scan заповнених заглушок |
| E | Діфф замість всього `src/` | `module-auditor.md` (кроки 1, 3) | P1 | менший read на змінений модуль |
| D | Дешевий `freshness` дефолтом, `update --only` | `fx-doc.md` | P2 | менше зайвих повних прогонів |
| F | Drawer-walk під `--suggest-drawers` | `module-auditor.md` (крок 5) | P2 | прибирає безумовний скан `src/` |
| — | Фікс `manifest_append` (інтерполяція + проковтнуті помилки) | `setup.sh` | P1 (надійність) | надійний uninstall |
| — | Синхронізувати README / «READ BEFORE FIRST» | README.md, READ BEFORE FIRST | P2 (косметика) | актуальна дока |

**Рекомендований порядок:** A + B разом (ядро виграшу, поведінка для користувача не змінюється) → виміряти
до/після на одному модулі → E → C → D → F. Окремою гілкою — фікс `manifest_append` (надійність uninstall).
